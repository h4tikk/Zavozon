# T27 Реализовать фоновую проверку Minecraft

## Результат

Ответить 202 и отдельно проверить присутствие и владение.

## Пользовательские истории

[[US17 Привязка Minecraft]]

## Модели

[[M18 MinecraftLinkRequest]], [[M01 User]], [[M13 ReviewRequest]]

## Зависимости

- [[T09 Создать модель фоновой привязки Minecraft]]
- [[T13 Реализовать единое рассмотрение заявок]]
- [[T26 Реализовать уведомления только через бота]]
- [[D02 Утвердить подтверждение Minecraft и получателя вывода]]

## Работа

- Создать заявку и job после commit, status endpoint scoped к User.
- Minecraft::PlayersClient: фиксированный URL, timeouts, HTTP status, ограниченный body, проверенная JSON schema.
- CheckPresence записывает online/offline/failed с checked_at; offline не retry как сетевая ошибка.
- Manual verify в первой версии выполняет только admin, поскольку отдельное право minecraft review пока не вводится; через ReviewRequest; подтвердить уникальность нормализованного ника под транзакцией.
- Общий периодический snapshot онлайна — последующее улучшение при необходимости, без отдельного запроса на каждого User.

## Предлагаемые сервисы

Minecraft::RequestLink; Minecraft::PlayersClient; Minecraft::CheckPresence; Minecraft::ConfirmOwnership

## Входные точки

POST /minecraft-link-requests → 202; GET /minecraft-link-requests/:id

## Готово, когда

- [ ] Форма реального JSON подтверждена до написания парсера; в этой сессии endpoint не проверен.
- [ ] Timeout не создаёт offline и не подтверждает владение.
- [ ] Просроченная задача не применяет ник после новой подачи.

## Проверка

Проверять наблюдаемое поведение и ограничения БД, а не только наличие методов. Для рискованных операций обязательны rollback, повтор запроса и гонка. Набор сценариев: [[06 Проверка и готовность]].

Карточка описывает будущую работу. Наличие похожих полей в исходниках не означает, что задача выполнена.
