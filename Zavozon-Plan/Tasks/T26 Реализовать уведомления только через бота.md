# T26 Реализовать уведомления только через бота

## Результат

Сообщать о событиях без влияния сетевого сбоя на бизнес-результат.

## Пользовательские истории

[[US16 Уведомления через бота]]

## Модели

[[M17 TelegramNotification]], [[M01 User]]

## Зависимости

- [[T08 Создать TelegramNotification TelegramUpdate и AuditEvent]]
- [[T25 Реализовать Telegram webhook и команды]]

## Работа

- В одной транзакции события создавать outbox через Enqueue с delivery_key.
- Определять адресатов по матрице, объединять совпадающего User при нескольких ролях где уместно.
- Renderer шаблонов экранирует пользовательский текст; callback не содержит секретов и не даёт полномочия.
- Claim lease на запись перед отправкой; ограниченные retry/backoff, обработка rate limit и blocked bot.
- Сохранять message_id, допускать дубликат при потерянном ответе; stale-кнопки проверяются сервером.

## Предлагаемые сервисы

TelegramNotifications::Enqueue; TelegramNotifications::Render; TelegramNotifications::Deliver; TelegramNotifications::RecoverPending; Telegram::Client

## Входные точки

Пользовательского endpoint отправки на произвольный chat_id нет

## Готово, когда

- [ ] Выключенный worker не теряет pending запись.
- [ ] 429 учитывает retry_after, постоянная недоступность не создаёт бесконечный цикл.
- [ ] Личные сведения покупателя не уходят всем курьерам; sent не считается read.

## Проверка

Проверять наблюдаемое поведение и ограничения БД, а не только наличие методов. Для рискованных операций обязательны rollback, повтор запроса и гонка. Набор сценариев: [[06 Проверка и готовность]].

Карточка описывает будущую работу. Наличие похожих полей в исходниках не означает, что задача выполнена.
