# T28 Подключить API ошибки и безопасные вложения

## Результат

Тонкие контроллеры вызывают операции, получают actor из сессии и возвращают единый контракт.

## Работа

- Before action закрывает API по умолчанию; login/health/webhook имеют явно обоснованные исключения.
- Expected errors через rescue_from; неожиданные через настроенный exceptions app или middleware с проверенным порядком.
- JSON code/message/request_id; 401/403/404/409/422/503 без SQL и stack trace наружу.
- Strong params не пропускают владельцев, статусы, суммы и права; pagination и rate limits.
- Подготовить Active Storage migrations и хранилище: в текущем schema таблиц вложений нет; проверить доступность файлов при перезапуске контейнера, лимиты, MIME/содержимое и сохранение доказательств.
- Фото товара публично по политике; payment evidence/withdrawal evidence только авторизованным владельцам и ревьюерам.

## Предлагаемые сервисы

Api::ErrorPresenter; Authentication concern; object policies; Evidence access

## Входные точки

Контракты перечислены в 05 API и события; CORS только нужного origin

## Готово, когда

- [ ] 401 не превращается в 200 с текстом ошибки.
- [ ] JSON-ошибки работают и для маршрутизации/неверного body, не только внутри action.
- [ ] Файл сохраняется после перезапуска приложения и доступен только по выбранной политике; Active Storage таблицы созданы в целевой среде.
- [ ] Запрос чужого вложения запрещён, подписанная ссылка не раскрывает доказательство всем адресатам.

## Проверка

Проверять наблюдаемое поведение и ограничения БД, а не только наличие методов. Для рискованных операций обязательны rollback, повтор запроса и гонка. Набор сценариев: [[06 Проверка и готовность]].

Карточка описывает будущую работу. Наличие похожих полей в исходниках не означает, что задача выполнена.
