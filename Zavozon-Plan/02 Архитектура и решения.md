# Архитектура и решения

## Принятые ограничения задачи

- Один Rails API и общая PostgreSQL для Mini App и бота.
- Пользователь идентифицируется проверенным Telegram ID; роли совместимы, не одно взаимоисключающее role.
- Уведомления только ботом, без отдельного in-app центра.
- Общий ReviewRequest хранит решение, reviewer остаётся связанным User внутри него.
- Один Wallet на User, доход продавца/курьера/владельца ПВЗ поступает этому User.
- Seller.paid_until устанавливается вручную уполномоченным администратором; отдельной подписки нет.
- Внешние игровые переводы подтверждаются вручную; автоматическая интеграция с Minecraft не предполагается.

## Связи

| Владелец | Связь | Объект |
| --- | --- | --- |
| User | один | Seller, Courier, Cart, Wallet |
| User | много | ApiSession, Purchase, собственные PickUpPoint |
| Purchase | много | Order, PaymentClaim |
| Order | много | OrderItem; снимки получателей и сумм |
| ReviewRequest | один target, много попыток на target | Seller/Courier/PickUpPoint/PaymentClaim/WithdrawalRequest/MinecraftLinkRequest |
| Wallet | много | WalletEntry и WithdrawalRequest |
| TelegramNotification | получатель User либо разрешённая группа | очередь сообщений ботом |
| TelegramUpdate | одно входящее событие | durable inbox с дедупликацией |

## Границы ответственности

Контроллер или webhook извлекает и проверяет транспортные данные, определяет actor и вызывает доменную операцию. Сервис проверяет полномочия/состояние, выполняет транзакцию, пишет аудит и outbox. Job загружает актуальный объект по ID и вызывает ту же операцию. Фронтенд не присылает доверенные суммы, владельцев, права, решение ревью или chat_id.

Не вводить generic CRUD service на каждую таблицу. Операции названы по действию пользователя и результату: PlacePurchase, ConfirmReceipt, RequestWithdrawal. Общий Reviews::Decide делегирует фиксированным обработчикам; не знает произвольные классы из входного payload.

## Источники истины

- Профиль хранит текущий допуск; ReviewRequest — историю решения. Историческое approved не меняется при suspension.
- OrderItem и Order хранят снимки сделки; текущий Product/владелец не переписывает историю.
- WalletEntry объясняет изменения; Wallet — текущий материализованный остаток. Обе записи меняются вместе.
- WithdrawalRequest хранит обязательство и фактическую выплату; одобрение review не означает перевод.
- TelegramNotification фиксирует намерение сообщить; ошибка отправки не отменяет бизнес-действие.

## Деньги

Предложение MVP: внешняя оплата покупки, Wallet только для доходов и выводов. Это не подтверждённая владельцем тарифная политика: детали [[D01 Утвердить расчёты и финансовые правила]].

Для каждого Order: total = products_amount + delivery_amount = seller_reward + courier_reward + pick_up_point_reward + platform_commission. Для Purchase: сумма Order.total = Purchase.total; сумма Order.products = Purchase.products; сумма Order.delivery = Purchase.delivery. Если экономика предполагает другие источники субсидии — явно моделировать их, а не ломать равенство.

Резерв вывода: balance не уменьшается до подтверждённой выплаты, reserved увеличивается при подаче. Доступно = balance − reserved. После выплаты уменьшаются оба. Отказ уменьшает только reserved. Неизвестный результат удерживает reserved до разбора.

Не заявляется полноценная двойная бухгалтерия: комиссия и остаток внешней кассы требуют отдельного отчёта сверки. При изменении масштаба можно перейти к ledger accounts, но не смешивать это с MVP без необходимости.

## Согласованность и повторы

- Транзакция охватывает состояние, журнал, аудит и outbox; внешняя сеть вызывается после commit.
- Единый порядок блокировок для операции документируется; кошельки блокируются по ID, конкурирующие approve/expire всегда блокируют Purchase прежде claim.
- Уникальные business keys защищают начисление, резерв и выплату независимо от Telegram update_id.
- Queue DB может быть отдельной: commit бизнес-БД и enqueue не атомарны. Durable inbox/outbox + периодический recovery закрывают разрыв.
- Доставка внешнего сообщения не exactly once. Финансовое действие имеет at-most-once применение внутри БД; ручной внешний перевод требует контроля и разбирательства при неизвестном результате.
