# M12 PaymentClaim

## Что есть сейчас

Принадлежность Purchase/Seller и условные проверки цели уже исправлены, nullable FK отражены в схеме. payment_claim_status передаётся без двоеточия. Purpose может быть NULL; отклонение пока хранится локально.

Основание: `app/models/payment_claim.rb; db/schema.rb:90–109`. Это статическое чтение исходников/schema, не проверка живой базы.

## Что изменить

- Исправить enum; сохранить purpose 0 purchase / 1 seller_access и существующие значения статусов.
- Сохранить доказательство и снимки ожидаемой суммы/получателя; заявленная сумма не является фактом перевода.
- Результат ревью перенести в ReviewRequest, payment_claim_status оставить состоянием платежной заявки.
- Сохранять verified_transfer_reference из доверенной истории переводов, если источник даёт такой идентификатор, и запретить повторное использование одного поступления для разных целей. При отсутствии такого ID нужна ручная сверка фактических переводов; повторный скриншот не доказывает новую оплату.
- Добавить applied_at или эквивалентный маркер единственного применения; учесть несколько claims на одну покупку.
- Срок seller access фиксировать отдельным аудируемым действием администратора, не вычислять из произвольной суммы клиента.

## Поля и ограничения базы

- Purpose/status NOT NULL после очистки старых записей.
- CHECK: purchase purpose требует только purchase_id, seller_access — только seller_id.
- claimed_amount nullable до заявления перевода; expected_amount > 0.
- verified_transfer_reference UNIQUE, когда указан; это доверенный идентификатор реального поступления, а не случайный ключ клиента. При нескольких источниках уникальность включает источник.
- Подтверждённая покупка имеет одно применение входящего платежа; нужен барьер на уровне Purchase, не только одного claim.

## Инварианты и границы

- Принадлежность цели user_id проверяется.
- Скриншот не означает принятие средств.
- Отклонение попытки не обязано отменять всю Purchase; новая попытка имеет собственное ReviewRequest.
